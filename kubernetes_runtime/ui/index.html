Request flow

One POST /v1/chat, from the client to the answer and its trace.

1Client → NodePortlocalhost:18080 → node :30080. kube-proxy picks a Ready endpoint per connection.
2MiddlewareServer span, in-flight gauge, request counter, x-served-by header.
3AuthBearer token checked against the mounted Secret file (current or previous).
4Agentinvoke_agent → chat (Groq or scripted) → execute_tool spans; loop up to 4 steps.
5AnswerJSON with tools used, token usage, pod, node and trace id.
6TelemetrySpans batch to the collector → Jaeger. The collector scrapes /metrics every 5s.

Autoscaling loop

Why a scale-out takes about 30–45 seconds end to end, and why scale-in is slower on purpose.

1Load risesrisk_score burns CPU on each request.
2metrics-serverReads kubelet CPU every 15s.
3HPAEvery 15s: desired = ceil(current × CPU% ÷ 60%), at most +100% or +3 pods per 15s.
4ScheduleNew pods spread across nodes (topology spread on hostname).
5Gate on probesStartup (~4s warm-up), then readiness adds the pod to the Service.
6Scale inAfter 60s below target: remove 1 pod per 30s. preStop + drain keep requests whole.

Readiness never checks the LLM provider

If Groq is down every pod would fail readiness together and the Service would have no endpoints. Upstream errors return 502 per request instead.

Secret rotation without restarts

1WriteSecret gets api-token=NEW and api-token-previous=OLD.
2Kubelet syncEach pod's mounted files are swapped atomically, usually within ~60s.
3Hot reloadThe app re-reads the file when its mtime changes and accepts both tokens.
4Switch clientsOnce every pod reports NEW's fingerprint, clients move to NEW. Zero 401s.
